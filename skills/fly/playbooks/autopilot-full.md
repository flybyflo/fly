### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge-ready, and the user decides every merge.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Here each PR's owner carries the lifecycle up to merge-ready, and the root keeps verification, countersigns, and audits.

**Gate.** Full autonomy covers reversible local work: building, verifying, fan-out, drafts. It does not cover commit, push, opening or updating a PR, or force-push. Each of those runs only when the operator's request explicitly grants that action, for example "owners may commit, push their own branches, and open PRs". No grant lets an owner merge, arm auto-merge, or push to `main` or `development`. Merges happen only for PRs the operator names after seeing the verdicts. Record the grant verbatim in every owner brief. A step below that needs an action the grant does not name stops at that step. The owner reports a ready summary (branch, head SHA, the exact command it would run, the evidence), and the root lists it as an open operator gate.

1. **Honor state-then-wait.** When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Use the GitHub CLI (`gh`) for every PR operation. Each owner works in its own git worktree. Prefer a T3 thread from `t3_thread_launch` with a worktree `workspaceStrategy`, since it can link and watch its own PR. An `Agent` with `isolation: "worktree"` also works, but a subagent cannot watch a PR, so the root watches for it. One owner per PR owns build, the first push, a ready PR, self-proof on the real artifact (the **prove-it-works** principle skill), skeptical triage of automated PR review bots per `../references/review-bot-triage.md`, a slop-strip (the `deslop` skill, `/deslop`), `/no-comments` (the **no-comments** skill), a rebase onto current trunk, and the babysit loop to green (`playbooks/babysit.md`). Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, opens the PR ready, never draft, and calls `link_pull_request` on it. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Every commit, push, and PR action here runs under the grant. Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after the slop-strip and `/no-comments`, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit then run in parallel with the swarm. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md and CLAUDE.md files and rules name for the touched paths, including the repo's review skill (for example `team-review`) when it has one. Run them on the committed head. A hook pass is not proof. To publish each rebase, push the owner's own branch with `git push --force-with-lease` after an `ls-remote` check, and only when the grant names force-pushing owner branches. Never force-push a shared branch, `main`, or `development`. Owners never merge.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off main, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private stack, managed with `gh stack` per the `gh-stack` skill.
4. **Swarm-verify every round before merge-ready.** A round starts at the owner's code-ready head SHA and at each later push that changes the PR's patch. At that SHA, fan out parallel independent verifiers per the **swarm** skill and aggregate to one verdict. Merge-ready needs a clean verdict from the round whose patch matches the head. Audit the receipts in the merge-ready report before the verdict. The lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (with the matching control skill, such as `control-cli` or `control-ui`, or a named driver where none exists). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No PR is reported merge-ready without the root's clean verdict. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red-first repro that covers every site with the same defect: a failing test where the repo's rules call for one, otherwise a repro receipt. Add that defect to the next round's review brief. The new head gets a fresh swarm and a fresh verdict, except for lane results that stay valid under the patch-id rule in `playbooks/shipping.md`.
5. **On a clean verdict the owner stops at merge-ready, and a fresh owner takes the next item.** The owner reports the head SHA, the verdict, and the exact merge command (`gh pr merge <pr> --squash`), then returns. The root adds the PR to the merge-ready list for the operator and calls `unwatch_pull_request` on it. When the operator names PRs to merge, land them through `playbooks/shipping.md`, which re-checks the verdict against the current patch and merges only once each PR is mergeable. A fresh owner picks up the next self-contained item from the queue, per fly's Subagents section.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners every hour. On the operator's go, arm it with T3 `schedule_task` (an `interval` schedule of one hour, bound to this thread) or Claude Code's `/loop 1h`, with a prompt that runs this tick. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from disk (`playbooks/autopilot-full.md` beside fly's `SKILL.md`) and audit the operation against it. Fix drift during that tick. Probe each owner with a generic liveness or status check (`t3_thread_read` for an owner thread, `task_status` for a delegated task), and collect the decision trails. Count only side effects as progress: commits, pushes, PR or check deltas, and store reports. Treat a lane that errors, or that passes its expected runtime without a side effect, as stuck. Stand it down and dispatch a replacement at once. Do not wait for a polite return. The tick judges an owner by its branch and the decision trail that step 2 requires, and it replaces an owner whose agent cannot start a turn. Each tick also runs the lane stuck test over the program's agent list (`t3_thread_list` and the root's own subagents) and over every owner's `children.tsv`. Whether or not a stop works, the root has the owner record each stuck subagent as stuck and, if its work is still needed, replace it. Each replacement that stalls gets the same steps. The root takes both steps when the owner cannot. A stall never proves or drops the work. End the tick only when no delegated work is left. Then delete the schedule with `delete_scheduled_task` or stop the loop.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. The merge-ready PRs waiting for the operator, and what each fresh owner took next. Countersigns granted and why. Open operator gates, including every action the grant did not cover. Where the collected decision trails live.
